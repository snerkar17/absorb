# Absorb

*Write it · tag it · map it.*

Absorb is a personal web app for capturing what you learn each day. You write a note, tag it with a category, and record where it came from. Every day is its own page. After 7 days logged, a **knowledge graph** unlocks — a map connecting the topics you've been learning, built entirely from your own data.

There is no AI anywhere in this app. The graph isn't generated by a model — it's the direct, deterministic output of counting your notes.

---

## What it does

- **Capture** — write a note, assign it one category (Science, History, Psychology, Finance, Tech News, Computer Science, Health/Wellness, Other), and record its source as free text.
- **Shelf** — logged days appear as cards on a home gallery, newest first, each showing its date, note count, and categories touched.
- **Day pages** — each day is self-contained. Notes never merge or move across days.
- **Streak & unlock** — the app counts days logged. At 7 days, the knowledge graph unlocks.
- **Knowledge graph** — a force-directed map of your topics: one bubble per category, sized by how many notes it has, connected by edges where two categories showed up on the same day. Thicker edges mean more shared days.

## Tech stack

| Layer | Choice |
|---|---|
| Frontend | [Next.js](https://nextjs.org) (App Router) + TypeScript, React 19 |
| Styling | Tailwind CSS v4 |
| Backend / DB / Auth | [Supabase](https://supabase.com) (managed Postgres, Auth, Row-Level Security) |
| Graph computation | Plain TypeScript (`GROUP BY`-style aggregation, no library) |
| Graph rendering | [`d3-force`](https://github.com/d3/d3-force) force-directed simulation, rendered to SVG |
| Hosting | [Vercel](https://vercel.com) |

There is no separate backend server. The Next.js app talks to Supabase directly from the browser using the public anon key; access control is enforced entirely by Postgres Row-Level Security, not application code.

## System design

### Architecture

```
Browser (Next.js client)
   │
   │  Supabase JS client, anon key
   ▼
Supabase
   ├─ Postgres (profiles, days, notes) — RLS enforced
   └─ Auth (session, auth.uid())
```

Nothing is computed or stored server-side beyond Postgres itself. The shelf and the knowledge graph are **never persisted** — they're recomputed from raw rows on every load. This keeps the data model tiny and guarantees the UI can never drift out of sync with what the user actually wrote.

### Data model

Three tables, defined in [`backend/supabase/migrations`](backend/supabase/migrations):

```
profiles  { id (= auth.users.id), created_at }

days      { id, user_id, date, status: "draft" | "finalized",
            created_at, finalized_at }
          UNIQUE (user_id, date)        -- one page per calendar date

notes     { id, day_id, user_id, text, category, source, created_at }
          category constrained to a fixed set via CHECK
```

Categories are a fixed list (not a database table) defined in [`frontend/src/lib/categories.ts`](frontend/src/lib/categories.ts), so the app, the DB constraint, and the graph all agree on the same set without an extra join. `user_id` is denormalized onto `notes` (not just `days`) so every table's RLS policy is a flat `user_id = auth.uid()` check — no joins required to enforce isolation.

Every table has RLS enabled with `select`/`insert`/`update`/`delete` policies scoped to `auth.uid()`, so a user can only ever read or write their own rows. There is no anonymous access — the whole app requires sign-in.

### Knowledge graph algorithm

Computed client-side in [`frontend/src/lib/graph.ts`](frontend/src/lib/graph.ts) from the user's notes (joined with their day's date). No AI, no external calls — just aggregation:

1. **Nodes** — group notes by `category`. Each category with ≥1 note becomes one node; its size is its note count.
2. **Edges** — for each day, look at the set of distinct categories logged that day, and increment a weight for every pair in that set.
3. Hand `{ nodes, edges }` to a `d3-force` simulation (`forceManyBody` + `forceCollide` + `forceLink` + `forceCenter`) to lay out bubbles so they repel, don't overlap, and cluster by connection strength.
